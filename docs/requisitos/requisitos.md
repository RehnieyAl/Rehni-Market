## Requisitos no funcionales (28)

| ID | Requisito | Categoría | Descripción | Criterio de aceptación | Referencia |
|---|---|---|---|---|---|
| RNF-001 | Autenticación basada en JWT (Access Token + Refresh Token) | Seguridad | RehniMarket debe implementar un mecanismo de autenticación basado en JSON Web Tokens (JWT) para proteger los recursos que requieren autenticación. El sistema debe utilizar un access token para autorizar las solicitudes a los recursos protegidos y un refresh token independiente para permitir la renovación de la sesión sin que el usuario tenga que ingresar nuevamente sus credenciales. El access token debe tener una duración limitada, mientras que el refresh token debe utilizarse exclusivamente para solicitar una nueva sesión de acceso. Los dos tipos de token deben ser identificables y no deben ser intercambiables. | Las rutas protegidas deben rechazar solicitudes sin autenticación. Una solicitud sin un access token válido debe recibir una respuesta HTTP 401. Un refresh token no debe poder utilizarse como access token. Un access token no debe utilizarse como refresh token. Los tokens deben ser validados antes de permitir el acceso al recurso solicitado. | `.docx`, sección 1. Seguridad |
| RNF-002 | Renovación silenciosa de sesión | Seguridad | El sistema debe permitir la renovación automática del access token cuando este haya expirado. La renovación debe realizarse utilizando el refresh token disponible, evitando que el usuario tenga que iniciar sesión nuevamente mientras su sesión siga siendo válida. El proceso debe ser transparente para el usuario y el frontend debe encargarse de reintentar la solicitud que originalmente falló debido a la expiración del token. | Una solicitud cuyo access token haya expirado debe generar una respuesta 401. El cliente debe detectar la expiración. Debe solicitar automáticamente un nuevo access token mediante el refresh token. La solicitud original debe poder reintentarse después de obtener el nuevo token. El usuario no debe tener que introducir nuevamente sus credenciales. | `.docx`, sección 1. Seguridad |
| RNF-003 | Autorización centralizada por rol y ruta | Seguridad | El sistema debe controlar el acceso a los diferentes recursos dependiendo del rol del usuario. La autorización debe estar centralizada y asociada a las rutas correspondientes, evitando que cualquier usuario autenticado pueda acceder a funcionalidades que no le corresponden. Los permisos deben determinar qué prefijos o rutas puede utilizar cada rol dentro de la aplicación. | Un usuario autenticado debe poder acceder únicamente a las rutas permitidas para su rol. Un usuario que no tenga permisos suficientes debe recibir HTTP 403. La validación del permiso debe realizarse antes de ejecutar la lógica principal del endpoint. Los roles administrativos deben disponer únicamente de las capacidades correspondientes a su nivel de privilegio. | `.docx`, sección 1. Seguridad |
| RNF-004 | Verificación de pertenencia de los recursos | Seguridad | RehniMarket debe garantizar que los usuarios y empresas únicamente puedan consultar, modificar o eliminar los recursos que realmente les pertenecen. La autorización no debe depender exclusivamente del rol. Además de comprobar que el usuario tenga permisos para realizar una operación, el sistema debe comprobar que el recurso solicitado pertenece al usuario o empresa que realiza la operación. | Un usuario o empresa no debe poder acceder o modificar recursos pertenecientes a otro usuario o empresa, incluso si conoce el identificador del recurso. Esta restricción debe aplicarse, entre otros, a: Pedidos. Direcciones. Productos. Cuentas bancarias. Recursos asociados a empresas. | `.docx`, sección 1. Seguridad |
| RNF-005 | Protección de contraseñas | Seguridad | Las contraseñas de los usuarios no deben almacenarse en texto plano. El sistema debe utilizar un mecanismo de hashing seguro que permita almacenar únicamente una representación irreversible de la contraseña. Para este propósito se utiliza bcrypt mediante las herramientas de seguridad configuradas en el backend. | Ninguna contraseña debe almacenarse en texto plano. La base de datos debe almacenar únicamente el hash. La validación de una contraseña debe realizarse comparando el valor introducido con el hash almacenado. No debe existir ningún endpoint que exponga la contraseña original. | `.docx`, sección 1. Seguridad |
| RNF-006 | Verificación obligatoria del correo electrónico | Seguridad | Las cuentas creadas en RehniMarket deben pasar por un proceso de verificación del correo electrónico antes de poder iniciar sesión normalmente. El sistema debe comprobar el estado de verificación de la cuenta y evitar la emisión de tokens de autenticación cuando el correo electrónico aún no haya sido confirmado. | Una cuenta no verificada no debe poder iniciar sesión. El sistema debe informar explícitamente que la cuenta requiere verificación. No deben generarse tokens de sesión para una cuenta que no haya sido verificada. La verificación debe realizarse mediante el mecanismo definido por el sistema. | `.docx`, sección 1. Seguridad |
| RNF-007 | Recuperación segura de contraseña mediante código de un solo uso | Seguridad | El sistema debe proporcionar un mecanismo seguro para recuperar el acceso a una cuenta cuando el usuario haya olvidado su contraseña. La recuperación debe realizarse mediante un código temporal enviado al correo electrónico registrado. El código debe tener una duración limitada y no debe poder utilizarse nuevamente después de haber sido consumido. | El usuario debe poder iniciar el proceso de recuperación mediante su correo. El código debe ser temporal. El código debe ser de un solo uso. Un código expirado no debe permitir restablecer la contraseña. El sistema no debe devolver ni exponer la contraseña anterior. No debe existir ningún endpoint que entregue contraseñas en texto plano. | `.docx`, sección 1. Seguridad |
| RNF-008 | Secretos y credenciales fuera del código fuente | Seguridad | Las credenciales y secretos utilizados por RehniMarket deben mantenerse fuera del código fuente. Las claves relacionadas con JWT, correo electrónico, base de datos, MinIO y otros servicios deben proporcionarse mediante variables de entorno, permitiendo modificar la configuración sin modificar el código de la aplicación. | No deben existir credenciales reales escritas directamente en el código. Los secretos deben obtenerse mediante variables de entorno. Los archivos de ejemplo deben contener únicamente valores de referencia. Los archivos .env reales deben excluirse del repositorio. | `.docx`, sección 1. Seguridad |
| RNF-009 | Almacenamiento seguro de sesión en el cliente móvil | Seguridad | La aplicación móvil debe almacenar los tokens de autenticación mediante mecanismos de almacenamiento seguro proporcionados por el sistema operativo. Los tokens no deben almacenarse en mecanismos de almacenamiento plano que puedan exponer las credenciales de sesión. | Los tokens deben almacenarse mediante SecureStore. No se debe almacenar la contraseña del usuario. El almacenamiento debe aprovechar los mecanismos de seguridad disponibles en Android e iOS. | `.docx`, sección 1. Seguridad |
| RNF-010 | Restricción de acciones administrativas sensibles | Seguridad | Las acciones administrativas que puedan afectar cuentas con privilegios elevados deben estar protegidas mediante una validación adicional del nivel de privilegio. Las operaciones relacionadas con cuentas de administrador y propietario no deben depender únicamente de una comprobación superficial del rol. | Una cuenta con rol administrador que no tenga privilegios de propietario no debe poder: Modificar cuentas de propietario. Bloquear cuentas de propietario. Asignar el rol de propietario. Ejecutar operaciones reservadas exclusivamente al propietario. | `.docx`, sección 1. Seguridad |
| RNF-011 | Paginación en listados de alto volumen | Rendimiento | Los recursos que puedan contener grandes cantidades de registros deben utilizar mecanismos de paginación. El sistema no debe devolver todos los registros disponibles en una única respuesta. La paginación debe permitir controlar la cantidad de información retornada y facilitar el procesamiento tanto en el backend como en los clientes web y móvil. Debe aplicarse especialmente a listados como: Pedidos. Usuarios. Empresas. Reseñas. Reportes. Movimientos de billetera. | Las respuestas de los listados deben proporcionar información relacionada con: Página actual. Límite de registros. Cantidad total de registros. Además, debe existir un límite que impida solicitar cantidades excesivamente grandes de registros. | `.docx`, sección 2. Rendimiento |
| RNF-012 | Consultas agrupadas para contadores | Rendimiento | Los contadores que agrupen información por estado, categoría o entidad deben calcularse mediante consultas agrupadas, evitando realizar múltiples consultas independientes para obtener cada contador. Esta estrategia busca reducir el número de operaciones realizadas contra la base de datos y mejorar la eficiencia de los servicios. | Un conjunto de contadores relacionados debe poder obtenerse mediante una consulta agrupada utilizando mecanismos como GROUP BY, evitando ejecutar una consulta individual dentro de un ciclo. | `.docx`, sección 2. Rendimiento |
| RNF-013 | Contrato consistente de errores entre backend y frontend | Usabilidad | Los errores generados por las operaciones de negocio deben mantener una estructura uniforme entre el backend y los diferentes clientes de RehniMarket. Cada error debe proporcionar información que permita al frontend identificar de manera consistente qué tipo de error ocurrió y mostrar la respuesta correspondiente al usuario. | Los errores de negocio deben proporcionar como mínimo: Un código identificador del error. Un mensaje descriptivo. El código debe pertenecer al catálogo compartido de errores y no debe depender exclusivamente de mensajes de texto libres. | `.docx`, sección 3. Usabilidad |
| RNF-014 | Restauración del contexto después del inicio de sesión | Usabilidad | Cuando un usuario intente ejecutar una acción que requiera autenticación, el sistema debe conservar el contexto de la acción antes de enviarlo al proceso de inicio de sesión.
